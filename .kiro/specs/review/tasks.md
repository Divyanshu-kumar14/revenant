- [x] 3. Implement the transition table and `InvalidTransition` (`src/review/state.ts`), keyed by action as `Record<ReviewAction, Transition>` so a new action fails to compile until it has a row. Five pairs are allowed: `accept` needs_review → published, `edit` needs_review → needs_review (status unchanged; the caller still writes audit), `reject` needs_review → rejected, `reject` published → rejected (Requirements 4.4/6.3), `reopen` rejected → needs_review. `queued` and `extracting` are neither sources nor targets, `accept` from rejected needs a reopen first, and `edit` from published is out because post-publication edit semantics are unspecified. `targetStatus(action, from)` throws `InvalidTransition` (`code: "INVALID_TRANSITION"`, `status: 409`, message `Cannot <action> an item in <from>.`). The table is a pre-check only: `reviewItem` must still guard its UPDATE with `WHERE id = ? AND status = ?` and treat zero changed rows as a lost race. Verify: `tests/unit/review-state.test.ts` runs all 4 actions over all 5 statuses, the 5 allowed pairs return their targets and equal the table's rows exactly, the other 15 throw `InvalidTransition` with 409 and the passed action and status, and no row targets `queued` or `extracting`.
- [x] 4. Implement `reviewItem` accept only (`src/review/actions.ts`); edit, reject and reopen throw "not implemented yet" until task 5. The signature is `reviewItem(db, decision, clock?)` and returns `ReviewOutcome` synchronously, because `node:sqlite` is synchronous and a sync body keeps the one transaction readable. `db` is a parameter so tests pass `:memory:`, and one clock instant is shared by `items.updated_at`, `records.published_at` and the audit `created_at`. `zod` validates shape only (types, enums, array bounds, length ceilings). Accept runs in one `BEGIN IMMEDIATE`: `getItem`, `targetStatus`, then `transitionItem` guarded by the read status with `error: null`, so a failed extraction's code is cleared. Zero changed rows throws `ConcurrentChange`. The transaction then upserts `records` on `item_id` with `reviewed_by` and `published_at`, replaces the item's `item_entities` links, and upserts entities on `(type, name_key)` with `displayName`/`nameKey`, first spelling winning and role `"depicted"`. It writes one `accept` audit row and rolls back on any throw. The errors are `ReviewValidationError` (`INVALID_FIELDS`, 400), `ItemNotFound` (`ITEM_NOT_FOUND`, 404), `ConcurrentChange` (`CONCURRENT_CHANGE`, 409) and `InvalidTransition` (`INVALID_TRANSITION`, 409). Title and date-display presence and date ordering are task 6. Verify: `tests/unit/review-actions.test.ts` reads `items`, `records`, `entities`, `item_entities` and `audit_events` directly, because `listPublished()` is archive task 1, and the inverted-dates case proves the transaction rolls back.
